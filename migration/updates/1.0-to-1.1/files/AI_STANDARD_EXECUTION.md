# AI_STANDARD_EXECUTION

> AI 编程标准 1.1 专用规范，按 AI_STANDARD.md 的任务路由按需读取。

> 前置：CORE、PROJECT、ENTITIES；输出：执行流程。

## 第 5 部分：执行协议

> 衔接：项目存在行为指导入口时，按当前任务和问题信号匹配，命中才展开，详情见 `AI_STANDARD_LEARNING.md` 第 6 节。接手、关键动作前、异常和交接复用现有流程；不要求每轮对话加载全部指导。

复杂项目接手采用“最小读取集合 + 状态判断 + 按需扩展”方式。最小读取集合不是完成条件；发现阻塞、未关闭缺陷、未回答问题、未验证变更、配置冲突或交接不完整时，必须读取相关实体和审计材料后再接手。

复杂实现应在 `DES` 或 `TASK` 中规划可验证的实现批次。简单变更可以一次完成；复杂变更按批次创建任务、变更集和验证记录，依赖批次满足进入条件后再推进；独立批次可按已确认分工并行。

### 5.1 协议目的

执行协议解决一个问题：**AI 在项目已配置后，如何接手、分析、修改、记录、交接，而不依赖对话记忆。**

执行协议是引导协议的后继。项目配置完成后，AI 按本协议工作。

---

### 5.2 接手流程

AI 每次接手项目，无论新会话、压缩恢复、还是换模型，都必须按固定流程接手。

#### 5.2.1 接手步骤

| 步骤  | 动作        | 读取                           |
| --- | --------- | ---------------------------- |
| 1   | 读记忆锚点     | `.ai/AI_ANCHOR.md`           |
| 2   | 读详细入口     | `.ai/AI_ENTRY.md`            |
| 3   | 读配置       | `.ai/PROJECT_PROFILE.md`     |
| 4   | 读索引       | `.ai/index.yaml`             |
| 5   | 按用户意图定位实体 | 相关 `TASK/BUG/CHG/REQ/ADR`    |
| 6   | 读当前真相     | `docs/current/` 相关文件         |
| 7   | 读不变量      | `docs/current/INVARIANTS.md` |
| 8   | 输出接手声明    | —                            |

规则：

- 禁止跳过接手流程直接开始工作。
- 禁止仅凭对话记忆判断当前状态。
- 已配置项目先读存在的 AI_ANCHOR；文件缺失则核实配置与当前记录，按授权恢复最小导航，不假装已经读取。未配置或纯讨论按 ONBOARDING/INTENT。
- 压缩恢复时，从步骤 1 重新开始。

#### 5.2.2 接手声明格式

```text
【接手声明】

- 已读：AI_ANCHOR, AI_ENTRY, PROJECT_PROFILE, index.yaml
- 当前阶段：F7 实现与验证
- 当前任务：TASK-0003
- 当前目标：实现模块 A 的接口 IF-0007
- 我理解的不变量：
  1. 模块 A 不得依赖模块 B
  2. 跨线程对象生命周期由 X 管理
  3. 公共头文件不得包含平台相关头
- 我不确定的地方：
  1. IF-0007 的错误处理是否用 std::expected
- 我计划的第一步：
  1. 读 IF-0007 和 DES-0012，确认错误处理策略
```


规则：

- 接手声明必须输出，不能省略。

- 不确定处必须列出，不能假装知道。

- 计划第一步必须具体，不能写“开始开发”。

- 接手声明写入当前 `SESSION`。

### 5.3 用户意图路由

AI 接手后先读取存在的 USER_INTENT.md 相关主题，区分讨论、候选理解与行动授权；模糊、局部明确、需求变化或探索性实现按 AI_STANDARD_INTENT.md 处理，再路由实体，不强行分类。

| 用户意图 | 路由                     | 流程         |
| ---- | ---------------------- | ---------- |
| 新需求  | `REQ`                  | 需求流程，见 5.5 |
| 设计变更 | `ADR` / `CHG`          | 变更流程，见 5.7 |
| 修复缺陷 | `BUG`                  | 缺陷流程，见 5.6 |
| 继续开发 | `TASK`                 | 任务流程，见 5.4 |
| 查询历史 | `change_log` / `audit` | 查询流程，见 5.8 |
| 交接   | `SESSION`              | 交接流程，见 5.9 |
| 不确定  | —                      | 先问，不要猜     |

规则：

- 意图不明时，先问用户，不要自行假设。

- 多个意图时，先处理阻塞项。

- 意图与当前阶段冲突时，先确认再执行。

### 5.4 任务流程

用于 `TASK` 的执行。

#### 5.4.1 步骤

1. 读 `TASK` 及其 `depends_on`、`related_to`。

2. 读相关 `REQ`、`DES`、`IF`、`ADR`。

3. 做影响分析，见 5.10。

4. 检查任务退出标准。

5. 执行实现。

6. 记录 Session。

7. 运行验证（按 `verification.policy`）。

8. 更新任务状态。

9. 更新 `change_log`。

10. 输出交接摘要。

#### 5.4.2 任务状态转移

状态集合和允许转移以 AI_STANDARD_ENTITIES.md 第 2.3 节为唯一依据，本节只定义进入状态的证据要求。

规则：

- 进入 `doing` 前必须输出接手声明。

- 进入 `blocked` 必须记录阻塞原因和解除条件。

- 进入 `done` 必须有证据。

- 进入 `verified` 必须有 `VER` 或等价证据。

- 跳状态必须记录原因。

#### 5.4.3 任务 Session 格式

```markdown
### Session-N · <时间> · <changeset>

- 目标：
- 操作：
- 证据：
- 结论：
- 下一步：
- 阻塞：
```

规则：

- 每次任务推进追加一个 Session。

- Session 默认只追加，不修改历史事实；已确认的冲突 CHGSET 引用可依 AUDIT 受控纠错修正，保留原件、映射和修复记录，不改写用户表达或原结论。

- Session 关键结论回写 `change_log`。

### 5.5 需求流程

用于 `REQ` 的创建和细化。

#### 5.5.1 步骤

1. 确认需求是否已存在，避免重复。

2. 若不存在，创建 `REQ`，状态 `draft`。

3. 与用户确认背景、目标、验收标准。

4. 需持续追踪的不确定项按 INTENT 创建或关联 OPEN。

5. 明确采用临时前提时，按启用配置记录 ASM 或等价来源。

6. 需求细化后更新状态。

7. 关联到 `TASK`、`DES`、`IF`。

#### 5.5.2 需求状态转移

状态集合和允许转移以 AI_STANDARD_ENTITIES.md 第 2.3 节为唯一依据，本节只定义进入状态的证据要求。

规则：

- 需求不要求冻结才能开发。

- `provisional` 需求可关联 `TASK`。

- 需求变化走 `CHG`。

- 废弃需求不删除，标 `deprecated`。

#### 5.5.3 需求验收标准

- 每条 REQ 保留验收标准位置；draft/exploring 可明确未定及其影响，正式实施相关范围前形成该动作所需的判据。

- 验收标准可以 `provisional`。

- 验收标准必须可验证，或标注不可验证原因。

- 验收标准变化走 `CHG`。

---

### 5.6 缺陷流程

用于 `BUG` 的修复。

#### 5.6.1 步骤

1. 读 `BUG` 及其 `related_to`。

2. 读相关 `IF`、`DES`、`ADR`、`INVARIANTS`。

3. 输出接手声明。

4. 在 `BUG` 追加 Session：目标、复现、环境、假设。

5. 复现缺陷。

6. 定位根因。

7. 做影响分析，见 5.10。

8. 写失败测试（若验证策略允许）。

9. 实现最小修复。

10. 运行验证。

11. 更新 `BUG` 状态。

12. 更新 `change_log`。

13. 输出交接摘要。

#### 5.6.2 缺陷状态转移

状态集合和允许转移以 AI_STANDARD_ENTITIES.md 第 2.3 节为唯一依据，本节只定义进入状态的证据要求。

规则：

- 进入 `reproduced` 必须有复现步骤和证据。

- 进入 `root_caused` 必须写根因。

- 进入 `fixing` 必须有修复计划。

- 进入 `fixed` 必须有修复证据。

- 进入 `verified` 必须有回归证据。

- 进入 `closed` 必须确认无遗留。

- 跳状态必须记录原因。

#### 5.6.3 根因分析要求

根因必须回答：

- 直接原因是什么？

- 根本原因是什么？

- 为什么之前没发现？

- 是否影响其他部分？

- 是否需要 `ADR` 或 `CHG`？

- 是否需要更新不变量？

规则：

- 根因不能只写“代码错误”。

- 根因必须可验证。

- 根因影响范围必须写入 Session。

#### 5.6.4 回归要求

- 修复必须有回归证据。

- 回归证据可以是测试、人工审查、日志。

- 无自动化测试时，用 `E1` 或 `E2` 记录。

- 回归证据写入 `BUG` Session 或 `VER`。

---

### 5.7 变更流程

用于 `CHG` 和 `ADR`。设计变更、配置变更、架构变更走此流程。

#### 5.7.1 步骤

1. 判断变更类型：决策变更走 `ADR`，执行变更走 `CHG`。

2. 创建 `ADR` 或 `CHG`，状态 `proposed`。

3. 做影响分析，见 5.10。

4. 与用户确认 L2/L3 变更。

5. 更新当前真相。

6. 旧决策标 `superseded`。

7. 确有迁移工作时生成或关联已启用 TASK；无迁移说明不适用。

8. 更新 `change_log`。

9. 输出交接摘要。

#### 5.7.2 变更状态转移

状态集合和允许转移以 AI_STANDARD_ENTITIES.md 第 2.3 节为唯一依据，本节只定义进入状态的证据要求。

规则：

- 变更不删除历史。

- 旧决策标 `superseded`，不删。

- 变更必须做影响分析。

- 变更必须关联受影响实体。

- 变更必须记录迁移和回滚。

#### 5.7.3 影响分析矩阵

每次变更至少检查以下维度，不相关标 `N/A`：

| 维度          | 检查内容                     |
| ----------- | ------------------------ |
| 需求/目标       | 是否影响 `REQ`               |
| 架构/不变量      | 是否影响 `ARCH`、`INVARIANTS` |
| 接口/ABI      | 是否影响 `IF`                |
| 数据/所有权/生命周期 | 是否影响对象模型                 |
| 并发/线程       | 是否影响线程模型                 |
| 错误处理        | 是否影响错误策略                 |
| 性能/资源       | 是否影响性能预算                 |
| 安全          | 是否影响安全边界                 |
| 构建/依赖       | 是否影响构建                   |
| 平台/编译器      | 是否影响平台支持                 |
| 文档/记录       | 是否需要更新文档                 |
| 验证/证据       | 是否需要更新验证                 |
| 发布/迁移/回滚    | 是否需要迁移或回滚                |

规则：

- 影响分析写入适用 CHG/ADR 或当前已启用工作记录，不强制为每次小修另建实体。

- 不相关项标 `N/A`，不能省略。

- 有影响项必须关联实体。

- 影响分析必须在执行前完成。

### 5.8 查询流程

用于历史查询。避免无目的遍历全库，完整审核按明确范围分批进行。

#### 5.8.1 查询路径

| 查询        | 读取路径                         |
| --------- | ---------------------------- |
| 实体历史      | 读实体 `change_log`             |
| 实体最近发生    | 读 `change_log` 最后 N 条        |
| 谁改过文件     | 读相关审计分片，过滤 `files`           |
| 所有 ADR 历史 | 读审计分片，过滤 `entities` 含 `ADR-` |
| 决策为何被改    | 读原 ADR + 过滤含该 ADR ID 的变更集    |
| 时间段历史     | 读对应审计分片                      |
| 变更集详情     | 按 changeset ID 定位审计分片        |
| 最近交接      | 读 `AI_ANCHOR.md`，按需读 SESSION |
| 跨实体影响     | 读 `index.yaml` 关系图 + 审计分片    |

#### 5.8.2 查询规则

- 优先每批读取一个实体与 1–2 个相关分片，必要时沿关联分批扩展并说明。

- 不无目的遍历全部历史；处理已发现问题可以按明确范围扩展。

- 禁止把全部历史加载进上下文。

- 归档默认不读，已授权问题确需历史证据时按关联读取。

- 查询结果必须引用变更集 ID。

### 5.9 交接流程

用于会话结束或阶段结束。

#### 5.9.1 交接摘要格式

```text
【交接摘要】

- 会话：SESSION-0012
- 阶段：F7 实现与验证
- 当前任务：TASK-0003
- 已完成：
  1. 实现 IF-0007
  2. 修复 BUG-0042
- 证据：
  1. 编译通过，见 VER-0005
  2. 人工审查，见 BUG-0042 Session-3
- 当前状态：
  - TASK-0003: doing
  - BUG-0042: fixed
- 假设：
  1. ASM-0003：错误处理用 std::expected
- 未决：
  1. OPEN-0003：是否支持跨平台
- 阻塞：
  1. 无
- 下一步：
  1. 验证 BUG-0042 回归
- 回滚点：
  1. CHGSET-2026-09-14-006
- 相关文件：
  1. docs/current/IF-0007.md
  2. docs/work/BUG-0042.md
```

#### 5.9.2 交接规则

- 交接摘要必须写入当前 `SESSION`。

- 交接摘要必须更新 `AI_ANCHOR.md`。

- 交接摘要必须包含回滚点。

- 交接摘要必须包含下一步。

- 交接摘要必须输出给用户。

- 分别说明开发完成、验证和文档收束情况；阶段收束审核未完成时写明范围及影响，不用一个“完成”代替三者，规则见本文件“阶段收束审核”。

### 5.10 影响分析

影响分析是执行协议的核心。任何修改都必须做影响分析，避免补丁式修改。

#### 5.10.1 最小影响分析

小修改（L0/L1）可做最小影响分析：

```text
【影响分析 · 最小】

- 变更：BUG-0042 状态更新
- 影响实体：BUG-0042
- 架构：N/A
- 接口：N/A
- 不变量：N/A
- 测试：pending
- 文档：BUG-0042
```

#### 5.10.2 完整影响分析

结构性变更（L2/L3）必须做完整影响分析，见 5.7.3。

#### 5.10.3 影响分析规则

- 影响分析必须在修改前完成。

- 影响分析必须写入实体或变更集。

- 不相关项标 `N/A`，不能省略。

- 有影响项必须关联实体。

- 影响分析结果必须用于更新当前真相。

### 5.11 压缩恢复

AI 感觉上下文被压缩、状态不明、或开始新会话时：

1. 重读 `.ai/AI_ANCHOR.md`。

2. 恢复标准版本、当前阶段、当前任务、下一步、最近交接。

3. 若锚点不足，读 `.ai/AI_ENTRY.md`。

4. 仍不足，按需读实体。

5. 输出接手声明。

6. 不要凭记忆继续，不要跳过重读。

规则：

- 压缩恢复从接手流程重新开始。

- 压缩恢复不继承之前的静默授权。

- 压缩恢复后必须输出接手声明。

- 压缩恢复后必须确认当前任务状态。

### 项目状态与批次判断

- 每个实现批次至少记录目标、任务、依赖、涉及实体、预期变更、退出标准、验证方式和回滚点；具体拆分由项目需求决定。
- 接手时至少区分正常推进、阻塞、未关闭缺陷、未回答问题、未验证变更、活动豁免或覆盖、配置冲突、交接缺失和状态不明；异常时扩展读取相关实体和审计材料。
- 验证失败时按性质关联或创建 BUG、OPEN 或新的 VER，不得覆盖原验证结果。

### 状态与验证异常处理

- 项目状态判断必须依据 AI_ANCHOR.md、PROJECT_PROFILE.md、当前实体文件、SESSION 和审计记录。
- 验证失败先判断方法和环境是否有效：方法变化按 ENTITIES 的 VER 语义判断追加执行或新建；需求不明确关联 OPEN；实现不符合已确定要求关联 BUG；无法判断时保留未知，只有明确采用临时前提才记录 ASM。不得覆盖原验证结果。
- 缺失的未启用实体影响追踪、验证或安全性时，任务进入 blocked；不影响当前工作时在已启用的记录中注明限制后继续，不递归创建被禁用的 OPEN。

### 状态复核时机

- AI 至少在接手前、进入新实现批次前、变更集完成后、验证结束后和交接前重新判断项目状态。
- 执行中发现状态变化时，必须暂停当前假设，更新相关实体后再继续。


### 批次完成与状态同步

- 批次完成时至少同步 TASK、CHG、VER、SESSION、AI_ANCHOR 和必要的聚合视图。
- 同步适用且已启用的记录后，启动本文件“阶段收束审核”，核实同步结果；不因审核自动创建或启用所有实体。
- 最小读取集合必须叠加当前任务直接关联的实体及影响当前动作的依赖（包括已完成但仍提供契约或证据的依赖）；项目正常推进不构成跳过关联文档的理由。
- 实施批次关联 TASK、BUG 或 CHG 的现有目标；实际变更涉及需求/设计/配置时按 CHG 流程，不为普通实现强制另建 CHG。一个批次可有多个 CHGSET，CHGSET 不跨批次；失败或回滚后的新修复使用新 CHGSET。

### 复杂需求与并行开发

- 当需求包含多个独立目标、验收主体、生命周期或风险边界时，应拆分为多个 REQ；不可独立演进的内容可以保留在同一 REQ。
- 并行开发优先按模块或系统边界划分，并为每个范围分配 TASK、实体和验证责任。
- 并行开发前必须完成需求、设计和依赖分析；若项目已指定需求/设计责任方，则由其负责共享需求、设计、接口和不变量的统一裁决，否则应向用户反馈并由用户决定裁决方式。
- 执行方只能在已分配范围内实现；发现需求、设计或共享部分存在疑问时，必须反馈给用户或项目已指定的需求/设计责任方，不得自行改变共享语义。
- 并行合并后，按项目预先定义的验证责任和验证计划确认结果，并同步相关实体状态、Session、审计和聚合视图。

### 持续运行项目交接

具有持续运行状态的项目，交接时按需记录运行中的工作、外部依赖、未处理事件、临时状态、恢复步骤和停止风险。

### 模糊事项与验证责任

- 发现需求、设计、技术约束、责任分工或边界不明确时，必须先沟通并记录用户决定；不得以临时猜测替代决定。
- 正式实现的依赖未满足时暂停受影响部分，独立工作可继续；经授权、以查明依赖为目的的探索按 AI_STANDARD_INTENT.md 处理。
- 复杂项目可以按模块或系统设置分领域验证和总体验证；是否采用分层由项目需求和验证计划决定。
- 分领域验证通过只代表局部结果，不能替代覆盖整体目标的项目整体验收。

### 阶段收束审核

#### 触发与范围

版本迁移也是必经触发点：应用转换前开展源文档收束审核，转换后、切换版本前开展目标文档收束审核；切换后复核实际版本与入口一致性。步骤及放行边界见 migration/MIGRATION.md，不能用批次曾经审核过或文件格式检查代替本次审核。

在一批次任务或里程碑完成、准备宣布相应范围完成时开展文档收束审核。普通变更沿用日常写入检查，不要求每次小改动全库审核。用户要求审核、发现反复不一致或历史混乱时也可以启动。批次未完成或工作中断时先保存检查点，标明已查、未查和恢复入口，不强行宣布收束。

批次审核先检查本批次产出/修改的记录、直接依赖、当前意图的相关主题、入口、索引及相关聚合视图。里程碑审核扩大到对应目标、验收、活动实体、未决事项和交接。发现证据链不完整时沿关联扩大范围，记录扩大原因；不自动读取全部历史。现有历史查询数量限制作为单次读取批量，不作为忽略已发现关联问题的理由。

#### 检查依据与执行

1. 明确审核对象、采用的标准版本、项目配置、既有授权、退出标准及证据范围。旧历史按形成时的规则解释，不按新版追认违规。
2. 先核对事实来源和当前状态，再按 AI_STANDARD_CHECKLIST.md 的阶段收束清单检查格式、真实性、跨文档一致性、流程完整性及读取效率。审核范围内未发现问题不等于全项目无问题。
3. 每项发现记录位置、依据、影响范围、处理分类和待办。引用不唯一时使用文件路径、段落/条目、时间和内容依据辅助定位；不得按重复 ID 去重。
4. 修补遵守既有声明、分级、确认和审计；事实核实后再更新索引、看板、锚点、入口及相关当前文档，不能机械选择最新时间戳或某单一字段作为真相。
5. 修补后复查改动及受影响引用，保留问题处理结果和仍未解决项。文档变化使结论过时时，只复核受影响范围；记录审核截止内容或 CHGSET，不声称永久有效。

#### 修补边界

- 依据明确：授权范围内修复失效链接、已核实状态的导航同步等；不能把一切文字修改都当作低级别变更。
- 事实缺失：寻找可访问证据，缺失仍保留未知和影响；不补造时间、用户确认、历史 CHGSET、测试结果或原始证据。
- 语义冲突：任务是否完成、需求是否变化、责任或验收分歧，向用户或指定责任方说明并核实。仅暂停依赖该结论的动作，不能以整理文档为由改变项目决定。
- 历史异常：主动核实并处理。重复 CHGSET 按 AI_STANDARD_AUDIT.md 的受控纠错流程建立唯一有效标识、修复可确认引用并保留原件和映射，不能只登记后继续使用歧义引用。其他终态或只读记录按各自规则追加更正；无法确认的事实不改写。
- 来源缺失：在与当前问题相关且可访问的实体、SESSION、审计、备份和项目资料中查找；找到后核实对应关系并补准确引用，找不到则记录查找范围、结果、限制及后续动作，不补造证据。用户明确本次不查时标为“未开展”，不得写成“未找到”。
- 并行工作：先确认本次修补范围和文件当前内容，保护其他执行者的更新；冲突按 AUDIT 流程处理，不直接用审核副本覆盖。

#### 结果、阻塞与记录

开发完成情况、验证情况和文档收束情况分别报告。关键验收证据缺失或错误时，不得宣布对应目标已验证；局部格式/导航问题可修补或登记后续，不自动阻断无关工作。已有“完成”状态出现反证时说明差异，按原实体转移规则处理；不能仅因状态冻结就忽略反证，也不由审核绕过转移规则。

审核范围和修补工作归入相关 TASK/CHG；证据写入已启用的 VER，或项目允许的实体会话/SESSION。不新增审核实体，不强制启用被禁用实体。VER 按验证事项记录审核范围/判据，每次执行追加 Run；不同对象修订的结果分别定位，closed 不表示审核通过。

SESSION 保存结论、未解决项、后续责任和时机、开发/验证/文档收束三项状态及恢复入口；实际写入由 CHGSET/审计追踪。无修改的审核如实记录，不虚构修补。摘要结构见 TEMPLATES。

审核记录本身也遵守声明与记录要求，但其生成不递归触发新一轮全量审核。先校验自身摘要和引用即可；若记录写入又改变实质判断，则重新检查受影响结论。

审核和修补必须向用户报告：处理前说明问题及拟修改范围，处理后说明实际修补、依据、复查及同步结果；未解决或未开展项列出原因、影响和下一步。已有授权范围内不重复索要确认，但不得静默修改或静默略过问题；无修改的审核也报告结果。

文档事实核实后，才按 AI_STANDARD_LEARNING.md 提炼可复用经验；未核实原因只能作为候选假说，不能转成已验证指导。
