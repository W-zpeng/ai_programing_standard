# AI_STANDARD_CHANGE

> AI 编程标准 1.0 专用规范，按 AI_STANDARD.md 的任务路由按需读取。

> 前置：CORE、ENTITIES、PROJECT；输出：变更和写入规则。

## 第 6 部分：可见性协议

### 6.1 协议目的

可见性协议解决一个问题：**AI 可以在用户不逐字审查文档的情况下写文档，但绝不能在没有告知、没有回执、没有可审计记录的情况下写文档。**

用户通过对话获得可见性，而不是通过翻阅文档。AI 通过声明、回执、审计、静默标记，保证每一次写入都可知、可查、可回滚。

---

### 6.2 核心原则

以下为 MUST 级：

1. 默认不静默。
2. 所有写入必须遵守“先声明、后写入、写完回执”。
3. 禁止未声明写入。
4. 静默授权必须绑定具体变更集，单次有效，完成后自动失效。
5. 静默授权登记禁止使用“下一个变更集”这类模糊描述。
6. 静默仍需最小回执。
7. L2/L3 变更禁止静默。
8. 异常禁止静默。
9. 审计永远完整记录，不静默。
10. 多 AI 之间不继承静默授权。
11. 静默授权失效后，AI 必须主动宣告恢复标准回执。
12. 若用户未再次明确授权静默，AI 必须恢复正常回执。

---

### 6.3 变更集

变更集是可见性的最小单位。

#### 6.3.1 定义

一个变更集 = 一次逻辑写入事务，可以包含多个文件。

一个变更集必须满足：

- 同一目的。
- 同一关联实体集合。
- 同一级别。
- 同一会话。
- 完成后产生唯一变更集 ID。

#### 6.3.2 变更集 ID

格式：

```text
CHGSET-<YYYY-MM-DD>-<三位序号>
```


示例：

```text
CHGSET-2026-09-14-007
```

规则：

- 按天递增。

- 每天从 `001` 开始。

- 一旦分配，永不改变，永不复用。

- 变更集 ID 写入所有相关实体的 `change_log` 和 `last_changeset`。

#### 6.3.3 变更集边界

一个变更集只覆盖：

- 一次声明中列出的文件。

- 一次声明中列出的字段。

- 一次声明中列出的关联实体。

- 一次声明中列出的级别。

超出声明范围的写入，必须新开变更集，重新声明，重新请求授权。

---

### 6.4 写入前声明

AI 在写文档前，必须输出写入声明。

#### 6.4.1 声明格式

```text
【写入声明】

- 变更集：CHGSET-2026-09-14-007
- 操作：修改 / 新建 / 追加
- 文件：
  1. docs/work/BUG-0042.md
    - 状态：reproduced → fixing
    - 追加：Session-3（根因、修复计划、证据）
    - 字段：root_cause, fix_plan, evidence, status
  2. .ai/index.yaml
    - 更新：BUG-0042 的 status 字段为 fixing
- 关联：TASK-0101, IF-0007
- 级别：L1
- 原因：记录根因分析和修复步骤
- 影响：
  - 架构：无
  - 接口：无
  - 不变量：无
- 预计审计：docs/records/audit/2026-09.yaml#CHGSET-2026-09-14-007
- 是否需要确认：否
```

#### 6.4.2 声明规则

- 声明必须在写入前输出。

- 声明必须列出每个文件和每个字段。

- 声明必须给出级别。

- 声明必须给出关联实体。

- 声明必须给出影响。

- 禁止用“更新文档”“补充记录”这类模糊描述。

- 多个文件可合并为一个变更集，但必须逐个列出。

- 用户可回复“继续”“等一下”“只改状态”“展开”等。

---

### 6.5 写入后回执

写入完成后，AI 必须输出回执。

#### 6.5.1 回执格式

```text
【写入回执】

- 变更集：CHGSET-2026-09-14-007
- 状态：已完成
- 文件：
  1. docs/work/BUG-0042.md
    - 状态：reproduced → fixing
    - 追加：Session-3
    - 字段变更：root_cause, fix_plan, evidence, status
  2. .ai/index.yaml
    - 更新：BUG-0042.status = fixing
- 审计：docs/records/audit/2026-09.yaml#CHGSET-2026-09-14-007
- 影响：
  - 架构：无
  - 接口：无
  - 不变量：无
- 待确认项：无
- 回滚点：CHGSET-2026-09-14-006
- 下一步建议：运行编译验证
```

#### 6.5.2 回执规则

- 回执必须在写入后输出。

- 回执必须与声明一致。

- 回执必须给出审计入口。

- 回执必须给出回滚点。

- 回执必须列出待确认项。

- 回执必须简短、结构化、可扫读。

- 禁止用“已完成”一个词代替回执。

---

### 6.6 变更集审计

每个变更集写入审计分片。

#### 6.6.1 审计分片位置

```text
docs/records/audit/<period>.yaml
```

`<period>` 由 `docs.audit_shard_period` 决定：

- `monthly` → `2026-09.yaml`

- `quarterly` → `2026-Q3.yaml`

- `yearly` → `2026.yaml`

#### 6.6.2 审计条目格式

```yaml
- changeset: CHGSET-2026-09-14-007
  at: 2026-09-14T15:00:00+08:00
  actor: ai
  session: SESSION-0012
  entities: [BUG-0042, TASK-0101]
  files:
  - path: docs/work/BUG-0042.md
    operation: modify
    fields: [status, root_cause, fix_plan, evidence]
    summary: "状态 reproduced → fixing；追加 Session-3"
  - path: .ai/index.yaml
    operation: modify
    fields: [BUG-0042.status]
    summary: "同步索引"
    level: L1
    reason: "记录根因分析和修复步骤"
    impact:
    architecture: none
    interface: none
    invariants: none
    tests: pending
    silent: false
    user_confirmed: false
    rollback: CHGSET-2026-09-14-006
    notes: ""
```

#### 6.6.3 分片头部摘要

每个分片头部有摘要，便于快速定位：

```yaml
period: 2026-09
changesets: 47
first: CHGSET-2026-09-01-001
last: CHGSET-2026-09-30-047
entities_touched: [BUG-0042, TASK-0101, IF-0007, ...]
levels: {L0: 30, L1: 12, L2: 4, L3: 1}
```

#### 6.6.4 审计规则

- 审计永远完整记录，不静默。

- 审计不删除，不修改历史条目。

- 审计必须包含 changeset、at、actor、session、entities、files、level、reason、impact、silent、user_confirmed、rollback。

- 审计分片超过阈值（默认 3 个月）移入 `archive/`。

- 归档不删除，只移位置。

### 6.7 静默写入

静默写入是可见性协议的重点。设计目标是减少打扰，但不失去透明。

#### 6.7.1 静默授权流程

正确流程：

1. AI 先输出**具体写入声明**。

2. 用户看了声明后，说“这次静默”。

3. AI 登记静默授权，**原样绑定该声明**。

4. AI 执行。

5. AI 输出最小回执，并声明静默授权失效。

规则：

- 禁止在未声明具体写入内容前请求或登记静默。

- 禁止先拿静默授权再决定写什么。

- 禁止用“下一个变更集”这类模糊描述。

- 静默授权登记必须包含具体文件、字段、级别、关联、有效期。

#### 6.7.2 静默授权登记格式

```text
【静默写入授权 · 已登记】

- 变更集：CHGSET-2026-09-14-007
- 绑定声明：上一条【写入声明】的完整内容
- 具体范围：
  - docs/work/BUG-0042.md：状态 reproduced → fixing；追加 Session-3；更新 root_cause/fix_plan/evidence/status
  - .ai/index.yaml：更新 BUG-0042.status = fixing
- 级别：L1
- 关联：TASK-0101, IF-0007
- 有效期：该变更集完成后立即失效
- 禁止级别：L2/L3
- 异常处理：失败/冲突/不变量违反时立即正常通知
- 审计：完整记录，不静默
- 后续：未再次明确授权，将恢复标准回执
```

#### 6.7.3 静默最小回执格式

```text
【静默写入 · 已执行】

- 变更集：CHGSET-2026-09-14-007
- 状态：已完成
- 文件：docs/work/BUG-0042.md, .ai/index.yaml
- 摘要：BUG-0042 状态更新为 fixing；追加 Session-3；索引同步
- 审计：docs/records/audit/2026-09.yaml#CHGSET-2026-09-14-007
- 待确认：无
- 静默授权已失效。后续恢复正常回执。
```

规则：

- 静默仍需最小回执。

- 最小回执必须明确说“本次为静默写入”。

- 最小回执必须明确说覆盖哪个变更集。

- 最小回执必须明确说静默授权是否失效。

- 最小回执必须给出审计入口。

#### 6.7.4 静默授权失效

- 静默授权以变更集为边界。

- 变更集完成后立即失效。

- 失效后 AI 必须主动宣告恢复标准回执。

- 后续若用户未再次明确授权，AI 必须恢复正常回执。

- 多 AI 之间不继承静默授权。

- 压缩恢复不继承静默授权。

#### 6.7.5 持续静默

用户可以显式授权持续静默，但必须有范围、有级别、有排除项、有期限。

```text
【持续静默授权 · 已登记】

- 范围：本会话
- 允许级别：L0
- 允许操作：
  - SESSION 追加
  - 状态字段更新（如 todo → doing）
  - 时间戳更新
  - 索引同步
- 排除操作：
  - 新增实体
  - 删除字段
  - 修改关系
  - 修改 REQ/DES/IF/ADR 的实质内容
  - 架构不变量变更
- 异常：正常通知
- 有效期：会话结束或用户说“停止静默”
- L1+：仍按标准回执
```

规则：

- 持续静默必须显式授权。

- 持续静默必须给出可验证范围。

- 持续静默默认只允许 L0。

- 持续静默不覆盖 L2/L3。

- 持续静默不覆盖异常。

- 持续静默不跨会话、不跨 AI。

#### 6.7.6 静默禁止情形

以下情形禁止静默，必须立即正常通知：

- L2/L3 变更。

- 写入失败。

- 冲突。

- 回滚。

- 不变量违反。

- 待确认项。

- 文件缺失。

- 状态非法。

- 权限不足。

- 实际变更与声明不符。

- 审计写入失败。

#### 6.7.7 静默与声明不符

执行前发现实际变更与声明不符：

```text
【静默授权暂停】
原声明为修改 BUG-0042.md 的状态和 Session。
执行前发现还需要修改 IF-0007 的接口契约，属于 L3。
静默授权不适用。
请确认是否继续，或调整变更范围。
```

规则：

- 实际变更超出声明范围，必须暂停。

- 必须重新声明，重新请求授权。

- 禁止在静默授权下扩大变更范围。

### 6.8 变更分级与可见性

| 级别  | 用户可见性            | 需确认    | 可静默 |
| --- | ---------------- | ------ | --- |
| L0  | 最小回执             | 否      | 是   |
| L1  | 回执 + 摘要          | 默认否    | 是   |
| L2  | 回执 + 影响分析        | 是      | 否   |
| L3  | 回执 + 影响分析 + 显式批准 | 是，必须显式 | 否   |

规则：

- 级别由内容决定，不由文件决定。

- 一次变更集只允许一个级别；混合时取最高级别。

- L2/L3 必须输出完整影响分析。

- L3 必须用户显式批准。

- 用户可配置 `gates.require_confirmation` 和 `gates.allow_silent`。

### 6.9 回滚机制

#### 6.9.1 回滚粒度

- 按变更集回滚。

- 按文件回滚。

- 按字段回滚。

默认按变更集回滚。

#### 6.9.2 回滚流程

1. 用户说“撤销 CHGSET-xxxx”。

2. AI 读审计分片，定位变更集。

3. AI 读 `rollback` 字段，确认回滚点。

4. AI 输出回滚声明。

5. AI 执行回滚。

6. AI 输出回滚回执。

7. AI 记录回滚变更集。

8. AI 更新 `change_log`。

#### 6.9.3 回滚声明格式

```text
【回滚声明】

- 回滚目标：CHGSET-2026-09-14-007
- 回滚到：CHGSET-2026-09-14-006
- 影响文件：
  1. docs/work/BUG-0042.md
  2. .ai/index.yaml
- 影响字段：
  1. BUG-0042.status
  2. BUG-0042.change_log 最后一条
- 级别：L1
- 原因：用户要求撤销
- 是否保留历史：是
```

#### 6.9.4 回滚规则

- 回滚不删除历史。

- 回滚本身是一个新变更集。

- 回滚必须记录原因。

- 回滚必须更新 `change_log`。

- 回滚必须更新 `index.yaml`。

- 回滚后旧变更集标记 `rolled_back`。

### 6.11 安静模式与通知疲劳

透明不等于刷屏。以下机制控制噪音：

| 机制   | 说明                                |
| ---- | --------------------------------- |
| 批量回执 | 一个任务内多次 L0 追加，合并为一个回执             |
| 安静模式 | 用户可开 `visibility.quiet_mode_default`，L0 不逐条通知，会话结束汇总 |
| 摘要优先 | 回执只列关键字段，不列完整 diff                |
| 变更聚合 | 按变更集聚合，不按文件逐个刷                    |
| 确认阈值 | 只有 L2/L3 才要求确认                    |
| 会话汇总 | 会话结束必须输出本次文档变更汇总                  |

#### 6.11.1 会话汇总格式

```text
【本次会话文档变更汇总】

- 标准回执：5 次
- 静默写入：2 次
- 变更集：CHGSET-2026-09-14-007, CHGSET-2026-09-14-009
- 待确认项：1 个
- 未决：OPEN-0003
- 审计入口：docs/records/audit/2026-09.yaml
```

规则：

- 会话结束必须输出汇总。

- 汇总必须包含所有静默写入。

- 汇总必须包含待确认项。

- 汇总必须给出审计入口。

- 即使用户开启安静模式，汇总仍然输出。

### 批次与写入声明

- 复杂变更的批次边界由设计方案和实施计划确定；写入声明对应当前批次的具体变更，不按文件数量或项目规模预设批次。

### 批次边界

- 写入声明对应当前实施批次的具体变更；批次边界由设计方案和实施计划确定。一个批次可以产生多个 CHGSET，但 CHGSET 不跨越批次。

### 并行开发中的变更边界

- 并行任务的变更边界由需求、设计和实施计划确定；优先按模块或系统隔离。
- 若项目已指定需求/设计责任方，共享需求、设计、接口和不变量由其统一裁决；否则反馈给用户决定。执行方发现疑问或冲突时必须暂停受影响修改。
- 每个并行范围使用独立 CHGSET，写入不得超出分配范围；共享语义经责任方更新后，相关任务必须重新读取并按新决定执行。
- 并行合并后的验证由项目验证责任和验证计划决定，不由本标准预设具体测试范围。
