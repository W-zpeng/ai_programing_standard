# AI_STANDARD_ONBOARDING

> AI 编程标准 1.0 专用规范，按 AI_STANDARD.md 的任务路由按需读取。

> 前置：CORE、PROJECT、TEMPLATES；输出：引导流程。

## 第 4 部分：引导协议

### 4.1 协议目的

引导协议解决一个问题：**项目配置和需求不应该要求用户先懂标准。** 用户只需要跟 AI 对话，AI 负责把模糊意图转成标准能读的实体文件。

引导协议是执行协议的前置。项目未配置时，AI 必须进入引导协议，禁止直接写代码。

---

### 4.2 启动条件


| 条件                                                 | 动作           |
| -------------------------------------------------- | ------------ |
| `.ai/` 不存在                                         | 进入引导协议       |
| `.ai/` 存在但 `PROJECT_PROFILE.md` 缺失                 | 进入引导协议       |
| `.ai/` 存在但 `PROJECT_PROFILE.md` 中关键字段为 `undecided` | 进入引导协议，补齐缺失项 |
| `.ai/` 存在且配置完整                                     | 进入执行协议       |

规则：

- 引导协议由 AI 主动发起，不等用户说“请引导”。
- 引导过程中禁止写代码。
- 引导过程中禁止创建未启用实体。
- 引导过程中的所有写入遵守可见性协议。

---

### 4.3 引导阶段模型

引导分 9 个阶段。阶段可以合并、跳过、回退，但必须记录原因。

| 阶段  | 名称     | 目标             | 主要产出                                 |
| --- | ------ | -------------- | ------------------------------------ |
| F0  | 项目启动   | 项目目标、范围、现状     | `PROJECT_PROFILE` 初稿、`REQ` 草稿        |
| F1  | 技术基线   | 语言、构建、平台、依赖    | `PROJECT_PROFILE` 技术段、`ADR`          |
| F2  | 验证策略   | 测试方式、证据等级      | `PROJECT_PROFILE` 验证段、`VER` 策略       |
| F3  | 文档与实体  | 目录映射、启用实体、门禁强度 | `PROJECT_PROFILE` 文档段 |
| F4  | 架构与不变量 | 分层、依赖规则、关键决策   | `ARCH`、`INVARIANTS`、`ADR`            |
| F5  | 需求细化   | 需求、开放问题、假设     | `REQ`、`OPEN`、`ASM`                   |
| F6  | 任务分解   | 任务、依赖、里程碑      | `TASK`、`board`                       |
| F7  | 实现与验证  | 执行、记录、交接       | `SESSION`、`VER`、`CHG`                |
| F8  | 变更与复盘  | 设计变更、影响分析      | `CHG`、`ADR` 更新                       |

规则：

- F0–F3 是配置阶段，F4–F5 是设计阶段，F6–F8 是执行阶段。
- F7–F8 由执行协议接管，引导协议只负责 F0–F6。
- 用户可随时说“先跳过”，AI 记 `OPEN`。
- 用户可随时说“回到 F1”，AI 记录并回退。
- 每个阶段有退出检查点，见 4.7。

---

### 4.4 问题库

问题库定义 AI 在引导中要问什么、为什么问、怎么展示、写到哪。

#### 4.4.1 问题定义结构

```yaml
id: Q-BUILD-001
topic: build_system
stage: F1
question: "这个项目用什么构建系统？"
why: "构建命令会写入 PROJECT_PROFILE，供后续 AI 执行和验证使用。"
options:

- key: cmake
  label: "CMake"
  description: "跨平台，C++ 生态主流"
  default: true
- key: bazel
  label: "Bazel"
  description: "大规模、多语言、强依赖管理"
- key: make
  label: "Make"
  description: "简单、轻量"
- key: custom
  label: "自定义/其他"
- key: undecided
  label: "暂不确定"
  action: create_open
  detect:
- "CMakeLists.txt"
- "WORKSPACE"
- "Makefile"
  follow_up:
- "构建命令是什么？"
- "是否需要交叉编译？"
  writes_to:
- PROJECT_PROFILE.build.system
- PROJECT_PROFILE.build.build_command
```



#### 4.4.2 核心问题库

#### 4.4.3 检测优先

AI 在提问前必须先检测项目现状：

- 扫描常见构建文件、目录结构、已有文档。

- 如果检测到已有配置，AI 提议：“我检测到 X，是否采用？”

- 用户确认后写入配置，不重复提问。

- 检测不替代提问，但减少提问量。

规则：

- 检测结果必须写入 `PROJECT_PROFILE` 的 `notes` 或对应字段。

- 检测结果与用户回答冲突时，以用户回答为准。

- 检测不到时，正常提问。

### 4.5 对话模板

AI 提问必须遵循统一格式，保证用户能轻松回复。

#### 4.5.1 标准提问格式

```text
【阶段 F1 · 技术基线 · 第 2/5 项】
问题：这个项目用什么构建系统？
为什么问：构建命令会决定后续 AI 如何编译和验证。
选项：
 A. CMake（推荐，C++ 生态主流）
 B. Bazel（适合大规模多语言）
 C. Make（轻量简单）
 D. 其他/自定义
 E. 暂不确定，先记录为开放问题
你可以直接回复 A/B/C/D/E，也可以补充说明。
```

规则：

- 必须标明阶段和进度。

- 必须说明为什么问。

- 必须给出选项，含默认和推荐。

- 必须支持“暂不确定”。

- 必须支持自由补充。

- 禁止一次问超过 3 个问题。

- 禁止开放式提问，除非问题本身无法选项化。

#### 4.5.2 批量确认格式

用户可要求批量回答或全选默认：

```text
【批量确认 · F1 技术基线】

- Q-LANG-001：C++20
- Q-BUILD-001：CMake
- Q-BUILD-002：cmake --build build
- Q-DEP-001：vcpkg
- Q-PLAT-001：无交叉编译
  你可以直接回复“全部默认”，或逐项修改。
```

规则：

- 批量确认后逐项写入配置。

- 批量确认后输出写入回执。

- 禁止在批量确认中隐藏未回答项。

#### 4.5.3 跳过格式

用户说“先跳过”时：

```text
【跳过登记】

- 问题：Q-VER-001 验证策略
- 状态：OPEN-0003
- 影响：后续 TASK 无法确定证据等级
- 再确认时机：F6 任务分解前
- 是否阻塞：否
```

规则：

- 跳过必须创建 `OPEN`。

- `OPEN` 必须记录影响和再确认时机。

- 跳过的关键项在退出检查点会再次提醒。

---

### 4.6 落盘规则

用户回答后，AI 必须：

1. 写入对应实体或 `PROJECT_PROFILE`。

2. 如果 `undecided`，创建 `OPEN`，记录影响和再确认时机。

3. 如果用户改了之前的决定，创建 `CHG`，更新当前真相，旧值标 `superseded`。

4. 在 `SESSION` 里记录“本次引导问了什么、用户选了什么、为什么”。

5. 更新 `index.yaml`。

6. 输出写入回执。

7. 更新 `AI_ANCHOR.md` 的当前阶段。

规则：

- 落盘必须走可见性协议。

- 禁止先落盘后声明。

- 禁止批量落盘后只给一个模糊回执。

- 落盘失败必须立即通知，不得静默重试。

---

### 4.7 阶段退出检查点

每个阶段有退出检查点。关键项必须已定或已标 `OPEN`，否则不得进入下一阶段。

| 阶段  | 退出检查点                           |
| --- | ------------------------------- |
| F0  | 项目名称、目标、范围、成熟度、平台已定或标 `OPEN`    |
| F1  | 构建系统、构建命令、依赖方式已定或标 `OPEN`       |
| F2  | 验证策略、证据等级已定或标 `OPEN`            |
| F3  | 文档角色映射、启用实体、门禁强度已定或标 `OPEN`     |
| F4  | 分层、依赖规则、关键不变量、关键决策已定或标 `OPEN`   |
| F5  | 核心需求、验收标准、开放问题、假设已定或标 `OPEN`    |
| F6  | 里程碑、任务分解、依赖、退出标准、第一步已定或标 `OPEN` |

规则：

- 检查点不通过时，AI 必须提醒用户。

- 用户可通过 `OVR-xxxx` 强制进入下一阶段，但必须记录覆盖范围和风险。

- 检查点通过后，AI 更新 `AI_ANCHOR.md`。

- 检查点通过后，AI 输出阶段交接摘要。

---

### 4.8 引导协议与执行协议的衔接

- 引导协议产出 `PROJECT_PROFILE`、`REQ`、`ARCH`、`ADR`、`OPEN`、`ASM`、`TASK`。

- 执行协议读这些文件，不需要重新问用户。

- 执行中发现配置缺失或过时：
  
  - 创建 `OPEN` 或 `CHG`。
  
  - 在下一次交互中按引导协议向用户确认。
  
  - 确认后再继续。

- 引导协议和执行协议之间的切换点：F6 完成，进入 F7。

- 切换时必须更新 `AI_ANCHOR.md` 的 `current_stage`。
