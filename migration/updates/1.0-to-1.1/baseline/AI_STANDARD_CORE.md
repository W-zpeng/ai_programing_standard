# AI_STANDARD_CORE

> AI 编程标准 1.0 专用规范，按 AI_STANDARD.md 的任务路由按需读取。


## 第 1 部分：核心原则与约束等级

### 1.1 核心原则

以下原则是标准的宪法层，不可协商。所有协议、模板、项目配置都必须与之一致。

#### P1 当前真相与历史记录分离

- 当前真相是活文档，只反映现在。
- 历史记录只追加，不删除，旧内容标记 `superseded/deprecated/archived`。
- 任何设计变更，先更新当前真相，再在历史记录中留痕。
- 禁止用历史记录覆盖当前真相，也禁止用当前真相删除历史。

#### P2 一个实体一个文件，内部追加会话

- 每个实体（需求、任务、缺陷、决策等）对应一个文件。
- 同一实体的多次操作，追加到同一文件内的会话记录中。
- 只有出现新实体时才新建文件。
- 禁止为小修复、小调整、小状态变化新建文件。

#### P3 稳定 ID，永不复用

- 每个实体有稳定 ID，格式由实体类型 + 编号组成，例如 `BUG-0042`。
- ID 一旦分配，永不改变，永不复用。
- 即使实体被废弃，ID 仍保留在历史中。
- 代码、提交、文档、审计之间通过 ID 互链。

#### P4 状态机驱动

- 每个实体有明确状态集合，状态之间按允许的转移规则变化。
- 状态变化必须记录时间和原因。
- 禁止跳状态而不记录原因。
- 禁止在未记录状态的情况下继续工作。

#### P5 任何代码修改必须关联实体

- 每次代码修改必须关联 `TASK`、`BUG` 或 `CHG` 之一。
- 禁止无关联的代码修改。
- 提交信息必须包含实体 ID。
- 关联关系必须写入实体文件和审计。

#### P6 先声明后写入，写完必回执

- 所有文档写入前，AI 必须输出写入声明。
- 所有文档写入后，AI 必须输出写入回执。
- 禁止未经授权的静默写入。
- 静默授权必须绑定具体变更集，单次有效，自动失效。
- 审计永远完整记录，不静默。

#### P7 接手声明与交接摘要

- AI 接手时必须输出接手声明：读到什么、目标、理解的不变量、不确定处、第一步。
- AI 结束前必须输出交接摘要：已完成、证据、状态、假设、未决、下一步、回滚点。
- 交接摘要写入实体文件和 `AI_ANCHOR.md`。

#### P8 偏离必须记录

- 任何偏离标准的行为，必须记录为 `WAIVER` 或创建 `OVR-xxxx`。
- 豁免必须有理由、影响、有效期、责任人。
- 禁止默默偏离。
- 豁免不删除历史，不覆盖标准。

#### P9 模型无关，工具无关

- 标准只使用纯文本、Markdown、YAML。
- 标准不依赖任何 AI 工具、模型、插件、IDE 的特有能力。
- 标准只依赖最大公约数：AI 能读文本、能写文本。
- 项目配置中不记录 AI 工具、模型、能力、插件信息。

#### P10 用户不需要审查文档

- 用户通过对话推进项目，不通过翻文档。
- 文档由 AI 生成、维护、审计。
- 用户通过写入声明、写入回执、静默标记、交接摘要获得可见性。
- 用户可随时要求展开、暂停、回滚、撤销，但不需要主动审查。

#### P11 允许不确定与渐进

- 需求可以 `draft/exploring/provisional`。
- 设计可以 `sketch/refined/stable`。
- 架构可以 `provisional`。
- 不确定记录为 `OPEN`，临时假设记录为 `ASSUMPTION`。
- 禁止因为“还没定”而阻塞推进；也禁止因为“先做”而丢失记录。

#### P12 软门禁优先于硬阻断

- 标准通过自检、声明、回执、豁免、审计形成约束。
- 默认不使用 CI 阻断开发。
- CI 可选，仅作报告和提示。
- 用户可配置门禁强度，但标准默认软门禁。

### 1.2 约束等级

标准中的每一条规则都有约束等级。AI 必须按等级处理。

| 等级                | 含义      | 偏离处理                         |
| ----------------- | ------- | ---------------------------- |
| `MUST`            | 必须遵守    | 偏离必须记录 `WAIVER` 或 `OVERRIDE` |
| `SHOULD`          | 推荐遵守    | 偏离需说明理由                      |
| `MAY`             | 可选      | 无需说明                         |
| `PROJECT_DEFINED` | 由项目配置决定 | 按 `PROJECT_PROFILE` 执行       |

约定：

- 未标注等级的规则，默认为 `MUST`。
- 涉及 P1–P12 核心原则的规则，均为 `MUST`。
- 涉及格式、模板、目录的规则，默认 `SHOULD`。
- 涉及具体验证策略、构建命令、启用实体的规则，为 `PROJECT_DEFINED`。

### 1.3 标准版本与迁移

- 标准有版本号，格式为 `MAJOR.MINOR`。
- `MAJOR` 变化表示不兼容变更，需要迁移。
- `MINOR` 变化表示兼容增强，无需迁移。
- 每个项目在 `AI_ANCHOR.md` 和 `PROJECT_PROFILE.md` 中记录所用标准版本。
- AI 接手时先确认标准版本，再按对应版本执行。
- 旧项目可以继续使用旧版本，也可以迁移；迁移必须记录为 `CHG`。
- 标准迁移不删除历史，不覆盖旧记录。

### 1.4 通用方法与项目约束分离

- 本标准规定分析、决策、记录、验证和交接的方法，不预先规定所有项目必须采用的具体技术约束。
- 项目应在需求分析阶段根据目标、范围、技术栈、风险和运行环境，判断需要哪些功能、质量、兼容性、安全和验证约束。
- 只有适用于当前项目的约束才写入 `REQ`、`ARC`、`DES`、`IF`、`VER`、`OPEN` 或 `ASM`。
- 一个项目中的具体约束不得自动推导为所有项目的通用规则。

### 1.5 适用性判断

- 需求分析应记录约束的适用性判断：约束项、是否适用、判断依据、记录实体和验证方式。
- 未判断适用性的技术属性不得被默认视为项目要求。

### 用户选择与核心原则

- 用户可以决定项目范围、约束和流程选择。
- 用户不能通过普通指令取消核心原则；确需偏离时必须创建 WAIVER 或 OVR。

### 规范冲突分层

- 标准文本互相矛盾时创建 `OPEN-xxxx` 并暂停相关动作。
- 项目配置选择较低能力时按项目配置执行并记录理由。
- 项目配置违反核心原则时创建 `WAIVER-xxxx` 或 `OVR-xxxx`。
- AI 违反已确定的项目配置或流程时创建 `INC-xxxx`。


### 状态冲突与用户选择

- 实体 frontmatter 状态和变更集审计是实体事实来源；最近 SESSION 提供过程证据；AI_ANCHOR.md 只提供导航，不覆盖实体状态。
- PROJECT_PROFILE.md 的配置字段独立作为项目配置来源，不与任务状态混用。
- 用户可以决定项目范围、约束和流程选择；不能通过普通指令取消核心原则，确需偏离时必须创建 WAIVER 或 OVR。

### 用户沟通与决策边界

- AI 发现需求、范围、技术约束、责任分工、模块边界、依赖或验证方式不明确时，必须向用户说明不明确之处、可能影响和可选方案。
- AI 可以提出建议，但不得替用户决定未经确认的项目范围、责任、技术方案或验收标准。
- 用户暂时无法决定时，创建 OPEN；无法安全继续时暂停相关工作。
