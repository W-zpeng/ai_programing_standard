# MIGRATION

> AI 编程标准 1.1 正式迁移规则。项目执行者只读发布材料；标准维护者的后续草稿不得覆盖已发布目录。未知来源或不完整材料不能作为迁移依据。

## 1. 材料与适用边界

用户手动复制或替换迁移入口、添加版本更新目录。复制材料不等于授权升级；用户已明确授权的范围无需重复确认，未授权采用目标版本时先提交评估。

发布目录必须自包含：UPDATE.yaml、具体 UPDATE.md、必需的文件内容或补丁、旧基线识别依据、检查及恢复说明。不得覆盖或删除已发布目录；修正应使用可区分的更新标识。总入口可以更新，但每个目录必须能独立解释其操作与适用条件；已开始迁移记录所用材料标识与内容摘要/校验值，中途材料变化先评估，不能静默换用。

版本号描述兼容性，不代替操作评估。MINOR 也可能需要新增文件和初始化可选能力。强制规则使原合规项目不再合规时必须评估不兼容影响。没有已发布路径时只做评估，不套用工作模板迁移。跨版本按声明路径逐步执行，各步记录和验证。

## 2. 评估与保护

1. 读取项目版本、入口、配置、索引、活动实体及未完成迁移。版本信息冲突先核实，不猜测来源版本。
2. 比较更新清单与实际文件，区分标准文件、项目实例、活动实体、历史记录、辅助文档和工具接入材料。解析实际 docs.roles，不写死默认路径。
3. 识别本地定制。能取得旧基线时做旧基线、本地文件和目标内容的三方比较；缺少可靠基线时保留本地文件并报告具体差异，不能声称自动辨认定制。清单的 add/rename/remove 均检查目标存在及引用，不盲目覆盖。
4. 评估受影响任务、依赖、并行写入和验证工具。仅暂停受影响范围；全局配置切换确实影响所有执行者时才扩大暂停。明确协调责任及恢复条件。
5. 提交转换、保留、跳过、待决清单及回退限制，按用户已授予的范围执行或请求缺失决策。不得按新版追认旧历史违规。
6. 在项目既有 records 角色下为迁移建立 CHG 和必要 TASK；实体未启用时先协商记录/配置方案，不能创建被禁用实体或陷入必须创建 CHG 才能启用 CHG 的循环。

## 3. 准备与执行

### 迁移前收束审核（应用转换的前置条件）

先对迁移范围内的源文档开展收束审核，不等到转换完成才检查。范围包括当前版本、配置、入口/锚点/索引、活动实体、被引用的验证和必要历史；发现断链或矛盾时沿关联扩大，不强制重审全部历史。已开展过的审核只有在范围和内容仍适用时才可复用。

依据项目当时采用的规则及实际证据，区分事实缺失、状态不同步、语义冲突和历史异常。按阶段收束审核方法记录发现，依据明确的修补在授权范围内执行；证据不足保留未知，实质分歧与用户或指定责任方核实。旧项目尚无新版审核流程时，使用本迁移材料的前置审核说明及旧项目允许的记录方式，不要求先升级才能审核。

将源记录分类为可转换、需先修补、可保留并注明限制、待决。缺陷会影响转换依据、结果解释或验收判断时，必须暂停对应转换；来源版本或共享依据无法确定时，暂停所有依赖它的步骤。无关历史问题可以登记后保留，但不能将错误或未知转换成已确认事实。用户确认升级本身不构成替代缺失证据的授权。

源审核发现重复 CHGSET 时按目标更新材料所提供的受控纠错方案处理：保留原件，建立唯一有效标识，修复可确认引用并记录歧义旧键的解释。不能在旧规范禁止改标识的情况下静默套用新版例外；迁移评估须明确这项纠错及用户授权范围，记录哪些改动是源纠错、哪些是结构转换。索引核实后主动同步；来源查找和所有已完成/未解决/未开展项均向用户报告，不能仅存于内部日志。

源审核结论、范围、来源修订/内容校验依据、修补及残余问题写入迁移 CHG 或项目允许的记录，核实后才进入 applying。修补前保存原始副本，保留“原始输入→核实/修补后的源→转换结果”的追溯；回退时依据已记录边界区分撤回转换与撤回源修补，不自动撤销经确认的独立纠错。

迁移 CHG 按 CHECKPOINT_TEMPLATE.md 保存检查点，不新增迁移实体。恢复副本和待应用内容放在项目 records 角色下独立的迁移工作目录，不能写入只读更新材料目录；具体路径记录到 CHG。不要求 Git。

修改前保存受影响文件的旧内容、路径、存在性、必要属性及内容校验值；新增文件也记录迁移前不存在。保存旧标准读取依据和确认范围。每一步具备 step_id、前置条件、操作、预期后置条件、验证及恢复方法。

按更新说明准备并应用增量。普通工作不得使用半转换状态；迁移操作按已确认方案和保留的旧规则执行，目标规则用于候选结果验证。项目文档转换按目标内容检查，不能因“还没切版本”跳过新版结构验证。

标准文件可先在工作目录准备；必须原地转换的项目记录在暂停受影响写入后操作。无法安全合并则保留各方内容，暂停该步骤并沟通。无需转换的历史保持原状，迁移 CHG 记录解释边界。

## 4. 检查、切换与恢复工作

完成标准文件一致性、实例转换、活动引用、新旧历史解释、各新增能力和本地工具检查。无必要转换也记录理由并验证。失败不切版本。

切换前执行目标文档收束审核：对照源审核结论、转换表和目标规范，检查语义、证据范围、用户确认及未决限制没有被丢失或扩大，入口和引用可用。格式检查和转换脚本成功不能替代该审核。影响迁移正确性的未解决问题阻止切换；允许保留的问题必须有依据、影响及后续安排。源审核、目标审核和切换后复核分别记录，不以单一“迁移通过”掩盖缺口。

检查通过后记录 switching 检查点，再同步目标标准、PROJECT_PROFILE、AI_ANCHOR、index 及相关入口。多文件修改不假定原子性：切换期间继续暂停受影响工作。复核版本字段、内容和引用一致后，记录 completed、SESSION、审计和回执，再恢复受影响工作。保留迁移 CHG 指针供后续接手及历史查询。

## 5. 中断与重复执行

接手先检查未完成迁移，再判断普通项目状态。逐步核对实际文件与前置/后置条件：满足后置条件则验证并标记已完成，不重复转换；满足前置条件才执行；两者均不满足则报告漂移并保留现场，不强行重试。

恢复或并行写入导致源内容、依赖或转换范围变化时，复核受影响的源审核结论；旧内容校验值一致也不能替代新发现的语义反证处理。审核失效的步骤不得沿用旧放行结论。

例如：存在 USER_INTENT 不重复覆盖；Run 使用源记录位置/内容依据去重，不依赖新分配编号判断重复；已转换 VER 不再次移动结果。切换中断时不能根据一个版本字段决定全局版本，必须检查所有受影响文件。

## 6. 撤回与降级

- 未切换：依据恢复副本撤回本次迁移，保留迁移尝试历史；比较当前内容是否仍为本次写入后内容，存在他人后续修改则先合并评估。
- 已切换但无后续工作：评估完整恢复旧规范与项目结构，验证一致性后记录恢复版本，不只修改版本号。
- 已有新版业务记录：按降级影响分析处理，不能声称无损回退；保留新历史及解释方式。缺少可行恢复路径时报告限制，不能强制覆盖。

标准回退与业务代码回退独立评估。恢复原文件也不删除迁移审计；只处理本次负责的变化。

## 7. 发布前检查

版本号、清单、基线、增量内容、实例动作、检查和回退说明必须齐备；占位符或 draft 材料不可执行。采用 FEATURE_MIGRATION.md 的能力专项检查及 REHEARSAL.md 演练。工具接入约束可能仍影响新版行为，向接入方说明差异，但项目升级不得修改工具系统提示词，项目规范不依赖特定接入文件名。
