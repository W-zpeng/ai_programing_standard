# AI 编程标准

AI 编程标准是一套面向用户与 AI 协作开发的通用规范。它帮助 AI 在理解用户意图的基础上，持续维护项目状态，按需求与依赖推进工作，并让每次重要决定、修改和交接都有据可查。

当前版本：**1.1**。

这套标准适用于从模糊想法到持续维护的不同阶段，也适用于已有代码的项目。它不限定语言、框架或开发方向；项目需要哪些技术约束、采用什么方案、如何分工，由用户与 AI 结合实际情况共同明确。

## 标准解决什么问题

AI 编程中的困难往往不只是代码实现，还包括：用户的想法尚未明确、对话中改变了目标、已有记录与当前状态不一致、换会话后丢失背景，以及多个执行者对职责和依赖理解不同。

本标准围绕这些问题组织协作：

- **理解意图**：允许开放讨论、局部明确和逐步细化，不把用户的举例、暂定想法或沉默当作实施决定。
- **按依赖推进**：根据当前目标形成需求、设计和实施安排；简单工作可以直接完成，复杂工作按有明确边界的批次推进。
- **持续维护状态**：把当前事实与历史记录分开，使 AI 能从项目文档恢复理解，而不只依赖对话记忆。
- **明确修改过程**：重要写入前说明范围，完成后报告结果；问题、失败和未完成事项不能静默略过。
- **协调并行工作**：按模块或系统划分职责，先分析依赖；共享部分有分歧时，反馈给用户或其指定责任方。
- **阶段收束**：在批次、里程碑和版本迁移等节点梳理记录，发现遗漏、错误和不一致后，依据事实修补并报告。
- **积累项目经验**：从实际工作中提炼有来源、有适用边界的行为指导，按需要展开，避免把完整复盘堆进每次上下文。

标准提供的是协作方法。它不会替用户决定产品目标，也不会因为有一套文档，就把复杂项目变成无需沟通的自动开发过程。

## 两层接入方式

使用本标准需要完成两件事：**把最小行为约束放入 AI 工具的固定上下文，并把完整规范放入项目目录。** 两者职责不同，缺一不能视为完整接入。

### 1. 将 AI_SKILL.md 的内容放入固定上下文

[AI_SKILL.md](AI_SKILL.md) 是最小行为约束的内容来源，包含接手项目、恢复上下文、定位规范、写入可见性等需要持续遵循的提醒。

**它不是复制到项目后就能直接使用的普通文档，也不是只在聊天中发送一次即可完成配置的文件。**

正确使用方式：

1. 打开 `AI_SKILL.md`，复制其正文内容。
2. 将内容放入实际 AI 编程工具支持的固定上下文或持续加载的指令位置。例如，工具的固定提示词、项目规则配置，或工具支持自动加载的 `AGENTS.md` 等文件。
3. 如果该位置已有项目规则，将内容作为独立部分合并进去，保留原有规则；发现冲突时先明确处理方式，不直接覆盖。
4. 确认所选配置确实作用于当前项目和后续会话。使用多个工具或执行环境时，分别处理其接入配置。

具体配置名称、文件名、作用范围和加载方式由所用工具决定。`AGENTS.md` 只是工具支持时的一种载体；单独创建同名文件，并不意味着所有工具都会加载。

例如，若所用工具会自动读取项目根目录的 `AGENTS.md`，可以在其中加入：

```markdown
## AI 编程协作约束

<在这里粘贴 AI_SKILL.md 的正文内容>
```

这里需要粘贴的是**实际约束内容**，不能只写一句“请阅读 AI_SKILL.md”就当作已完成固定上下文配置。

AI 不需要知道这些约束原本来自哪个文件。项目标准也不会要求 AI 识别、查找或读取 `AI_SKILL.md`；该文件不属于项目 `.ai/` 下的必读规范。

固定上下文保留最小约束，完整规范按需读取。这既有助于持续遵循协作方式，也避免把所有规则长期占用在上下文中。

### 2. 将项目规范放入 .ai/ 目录

在实际项目根目录建立 `.ai/`，将本版本的 `AI_STANDARD*.md`、`STANDARD_RELEASE.yaml`、`RELEASE_NOTES.md` 和 `migration/` 放入其中，保持相对路径。

`STANDARD_RELEASE.yaml` 列出本版本的项目标准文件。`AI_SKILL.md` 不随这些文件作为项目必读材料部署；它的内容通过上一步配置到工具侧。

项目布局示意：

```text
项目根目录/
├── AGENTS.md 或工具支持的其他固定上下文载体
│   └── 已合入 AI_SKILL.md 的正文内容
├── .ai/
│   ├── AI_STANDARD.md
│   ├── AI_STANDARD_CORE.md
│   ├── AI_STANDARD_ENTITIES.md
│   ├── AI_STANDARD_PROJECT.md
│   ├── AI_STANDARD_ONBOARDING.md
│   ├── AI_STANDARD_EXECUTION.md
│   ├── AI_STANDARD_CHANGE.md
│   ├── AI_STANDARD_AUDIT.md
│   ├── AI_STANDARD_INTENT.md
│   ├── AI_STANDARD_LEARNING.md
│   ├── AI_STANDARD_TEMPLATES.md
│   ├── AI_STANDARD_CHECKLIST.md
│   ├── STANDARD_RELEASE.yaml
│   ├── RELEASE_NOTES.md
│   └── migration/
└── 项目代码与其他资料
```

如果工具采用独立的固定提示词设置，就不需要为了这套标准额外创建 `AGENTS.md`。关键是约束内容进入该工具实际使用的固定上下文。

## 开始使用

接入后，可以直接向 AI 描述当前想法、问题或工作目标，不需要先学习实体编号或手工填写全部模板。

例如：

> 我有一个大致想法，但还没明确具体需求。先和我一起讨论，不要急着实现。

或者：

> 这是一个已有项目。先了解当前代码和项目记录，再分析这个功能应该如何接入。

AI 根据用户当前意图和项目状态开展工作：需要讨论时共同探索，已有明确目标时补充必要分析，在授权和依赖明确的范围内实施。项目尚未配置时，逐步补齐当前动作需要的信息，不要求用户先回答一整套固定问卷。

需要持久记录后，AI 按实际情况生成并维护：

- `.ai/PROJECT_PROFILE.md`：项目范围、构建方式、文档路径和采用规则。
- `.ai/AI_ANCHOR.md`：简短的当前状态和恢复入口。
- `.ai/AI_ENTRY.md`：项目阅读路径及当前重要信息。
- `.ai/index.yaml`：实体索引、状态和关系入口。
- 项目需求、任务、缺陷、变更、证据和会话记录。

默认文档目录分为 `docs/current/`、`docs/work/`、`docs/records/`、`docs/evidence/`，可根据项目配置调整。不要求所有项目启用全部实体，也不要求为了纯讨论创建空文档。

## 完整规范如何组织

[AI_STANDARD.md](AI_STANDARD.md) 是项目规范入口。AI 根据当前工作读取相关文件，而不是每次加载全部内容。

| 文档 | 主要职责 |
|---|---|
| `AI_STANDARD_CORE.md` | 核心原则、约束等级、版本及用户决策边界 |
| `AI_STANDARD_ENTITIES.md` | 实体、关系、状态与记录结构 |
| `AI_STANDARD_PROJECT.md` | 项目配置、文档拓扑、索引与当前状态 |
| `AI_STANDARD_ONBOARDING.md` | 项目接入和渐进配置 |
| `AI_STANDARD_INTENT.md` | 用户意图理解、共同探索与行动边界 |
| `AI_STANDARD_EXECUTION.md` | 日常执行、依赖、交接和阶段收束 |
| `AI_STANDARD_CHANGE.md` | 变更集、写入声明、回执和回退 |
| `AI_STANDARD_AUDIT.md` | 异常处理、并行冲突与历史标识纠错 |
| `AI_STANDARD_LEARNING.md` | 复盘提炼与渐进式行为指导 |
| `AI_STANDARD_TEMPLATES.md` | 项目记录的格式参考 |
| `AI_STANDARD_CHECKLIST.md` | 按场景使用的收束检查项 |

## 用户意图与项目经验

需要持续追踪时，项目维护一份 `USER_INTENT.md`，区分用户已明确表达的内容、AI 当前理解、待澄清部分和当前行动范围。它与需求、任务和会话记录关联，不替代用户决定，也不另建一套意图实体。

项目经验采用渐进式披露：入口说明何时适用，详细指导说明怎样行动，历史记录提供依据。普通工作只读取相关内容；经验发生反例或不再适用时，应修订或停用，不能让旧经验覆盖用户的新要求。

## 已有项目升级

已采用旧版标准的项目，应先阅读 [版本说明](RELEASE_NOTES.md) 和 [迁移说明](migration/MIGRATION.md)。用户手动添加更新材料后，AI 根据实际项目状态评估差异，按已确认范围处理，再切换项目采用版本。

1.0 到 1.1 的具体更新说明位于 [migration/updates/1.0-to-1.1/UPDATE.md](migration/updates/1.0-to-1.1/UPDATE.md)。本次包含记录语义调整，不能仅覆盖文件或修改版本号。项目已有决定、定制内容和历史记录需要保留并正确解释。

工具侧固定上下文与项目标准更新分别处理：如需调整接入约束，应由用户或接入方将新的正文内容合入工具配置；项目内迁移不会自动改写工具的固定提示词。
